# 建筑建模协作工作流

围绕用户的空间意图推进模型，保留原生编辑能力，让每轮修改有清楚边界、验证证据和可继续工作的版本。使用可用的 MCP 实际建模与核查；工具缺失时如实标记，不能以流程文字代替执行。

## 先定位阶段

| 阶段 | 本阶段成果 | 用户决策 |
|---|---|---|
| 前期方案探索 `exploration` | 简报、场地约束、空间意图；围绕真实分歧做少量不同候选、同视角比较与关键可行性检查，暂定项明确 | 判断探索方向 |
| 选定方案 `selection` | 用户选中的基线、选择理由、必须保留的空间关系、可调范围、未决项 | 明确选择方案 |
| 深入推敲 `development` | 可编辑墙板、围合、洞口、交通和家具占位；联合检查体量、视线、使用动作及关键接口 | 确认重大空间变更 |
| 最终精修 `refinement` | 门窗、栏杆、铺装、家具、灯具及收口完整；本体、邻接、范围外和原生编辑验证 | 确认影响设计的取舍 |
| 出图交接 `handoff` | 冻结主模型、原生面环与实例数据、构件/场景索引、坐标标高、证据和未决项；复杂平面及关键剖面底稿读取验证 | 确认阶段交付 |

接管、版本核对和用户手改保护贯穿五阶段。已有项目从适当阶段进入，缺陷返回受影响环节；无需重演已完成的选案。阶段内常规建模、修复和检查连续完成。已有授权不重复询问。探索时不提前投入精修节点，精修时不因局部技术方便重置总体空间关系。

不要为使用技能重走已经完成的阶段。先读项目现有交接入口、最近用户决策和实际模型，再补缺口。旧脚本、参数模型和旧说明不能覆盖用户最近的手工修改。

## 先接续项目事实

继续已有项目时，先从项目级 `AGENTS.md` 或固定根目录入口读取当前空间底表：稳定编号、功能、室内外属性、完成面标高、可达要求、连接关系、实体定位和证据来源。不要凭编号顺序、旧图或当前对话摘要重建已确认语义。表中与本轮无关的未知项不阻塞工作。

在生成相关几何前，将本轮区域展开为“编号＋功能＋标高＋联系对象”，与最新明确决定及实际模型核对；楼梯先核对起终点，家具先核对房间用途。有冲突先查证，不沿用错误编号继续生成。用户已确认的信息不再要求重复确认。

跨对话共享、冲突处理和当前表维护见 [references/project-context.md](references/project-context.md)。项目事实留在项目内；技能保存可复用方法，不写死某项目编号或尺寸。

## 每次开始时核对

1. 文件路径、源文件指纹、当前应用文档及其未保存状态。磁盘一致不代表窗口一致；不能静默还原未保存的手改。
2. 本轮目标、不能改的空间关系、允许改的构件，以及本轮交付到什么精度。
3. 单位、坐标轴、建筑零标高与模型坐标的换算；室内/室外边界和必须保留的现状。
4. 已有编号/实体ID、楼板和墙的真实轮廓、场景隐藏及互斥状态。包围盒只用于初筛。

只问会改变设计或导致破坏的关键歧义。已有授权和明确要求直接沿用；普通技术实现、验证和内部回退由 agent 完成。

## 执行

阶段通过条件见 [references/workflow.md](references/workflow.md)。使用 MCP 时先读 [接口与恢复](references/mcp.md)。圈图反馈、家具随动、风格调整及窗口保全，按需读取 [连续精修细则](references/continuous-refinement.md)。

每轮采用：**读取当前状态 → 核对空间意图与改动依赖 → 候选预检 → 原生写入并保存 → 重读核查本体、邻接与范围外 → 核对实际显示 → 绑定最终文件证据 → 简短交付**。候选计算通过不等于保存后的模型通过。

必须保留的做法：

- 先把空间、到达面、标高和联系关系讲清，再生成楼梯/洞口等复杂构件；视线贯通和通行连接分别判断。
- 分开判断户与户的独立、房间围合、临空防护和视觉联系。增加通高墙前核对其是否遮断已确认的错层、通高或内外关系；不能把功能名称直接翻译成封墙。小空间先验证体量、净使用面和主要动作，再细化五金；几何无碰撞不能替代空间效果审查。
- 门梯接口以接近、开门、落脚、转向、接梯的完整动作链检查，另查脚下连续实面；各版本分别登记覆盖范围。旧缺陷先复现，再以同版保存重读结果验证修复。
- 生成、原生写入、保存重读、核查、出图按依赖顺序推进；只并行独立任务。小轮次只重查失效证据，避免重复出图和报告。
- 场景保存、原生编辑撤销测试和其他会重写模型的动作均须在最终指纹冻结前完成。工具返回进程ID表示尚未完成；先取得退出码及输出，才能启动下游。核查分成新算、凭范围外比较继承和未查三类。
- 样件先行：墙板、开洞、楼梯、饰面或跨软件导入，先用一个真实关键局部验证方法再推广。
- SketchUp 是建筑主模型；家具/灯具等复杂资产在独立 Blender 进程和新文件副本中制作或续改，保留部件、修改器、材质和来源。资产记录米制尺寸、原点、朝向、安装基准、许可及输出；导入 SU 后重新核对尺度、材质、位置、原生编辑和操作空间。不要把“导出成功”当成往返通过。
- 原生可编辑是交付条件：检查分组、选面、推拉/等价编辑、撤销和保存重开；不能只验截图或网格封闭。文件保存重读、原生交互编辑、原生显示和派生图分别记状态；界面不可用时可交付已验证文件，但交互与显示仍须标为待查。
- 按使用动作组织家具，按实际支承面安装灯帘，按临空边界检查连续防护。无碰撞不等于好设计。
- 改完结构/墙板/梯段后，沿依赖关系更新栏杆、门窗、铺装、家具、灯帘和派生图纸；用最新完成面测量首末级和净空。
- 预留有意连接的记录；几何相交分为碰撞、有意嵌入和互斥表达，不能为实现“零相交”删掉连接。
- 修复碰撞时同时保留构件承担的围合、隐私、防护或支承功能；移位、内退或重做收口后检查功能连续性。删除构件只有在功能被明确取消或已有替代时才算完成。
- 建筑尺寸只有一个权威来源。派生文件可以有表现改动，但不得悄悄成为另一套建筑事实。

具体检查选用 [references/quality-checks.md](references/quality-checks.md)。工具取舍、编辑冲突和历史脚本复用见 [references/tools-and-recovery.md](references/tools-and-recovery.md)。不要把项目内某个板厚、坡度、梯宽、人数或软件版本作为所有项目的默认值。

## 文件基线辅助工具

`scripts/model_baseline.py` 仅使用 Python 标准库，读模型、写独立登记文件，**不会修改模型，也不会执行几何审查**。

```bash
python3 /absolute/skill/scripts/model_baseline.py init --source /absolute/model.skp --out /absolute/work/R01 --name 项目名
python3 /absolute/skill/scripts/model_baseline.py check --manifest /absolute/work/R01/manifest.json
python3 /absolute/skill/scripts/model_baseline.py register --manifest /absolute/work/R01/manifest.json --id native-check --file /absolute/report.json --kind report --depends source --note 保存后原生核查
```

初始化同时复制项目简报、轮次记录、交接模板。`register` 是操作者对来源关系的登记，不证明该报告覆盖了真实模型；必须先读报告并核对来源。每轮源模型改变后，在新的轮次目录重新 `init`，保留旧基线；不要改旧哈希让失效报告变绿。`check` 发现文件变化、缺失或派生依赖失效会返回非零退出码；一致只表示文件链一致。

## 交付尺度

普通精修轮次：留在用户要看的模型/场景，说明改了哪里、如何检查、还有什么未决；不默认增加长报告、渲染图或展示版本。

交付前把本轮产生的语义变更、当前模型入口及已废止决定回写项目底表；新对话应不依赖本轮聊天便能选对区域和版本。没有相关变化时只引用既有记录。

阶段交接：给唯一入口，含主文件和指纹、关键决策、坐标与标高、构件/场景索引、验证范围、未决项、派生成果来源和下一步。用 `assets/release.md` 按实际范围填写。结果分为设计确认、几何验证、文件验证与待专业深化，不混成一个“全部通过”。
